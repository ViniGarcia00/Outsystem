# Cadastro de Técnicos e vínculo do responsável das Instalações — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Substituir o responsável em texto livre das Instalações por um cadastro próprio de Técnicos, preservando integralmente os nomes já gravados no histórico.

**Architecture:** Cadastro novo `Tecnico{nome, ativo}` no molde exato de Vendedores (service + feature + 3 rotas + `CrudListView`/`CrudFormShell`). `Instalacao.responsavelAtual` (texto) vira `tecnicoResponsavelId` (FK, estado corrente, sem snapshot). `InstalacaoRegistro.responsavel` (texto) vira `tecnicoId` (FK) **mais** `responsavelNome` (snapshot histórico, derivado no service dentro da transação). Três migrations em sequência — criar tabela, vincular com backfill dirigido pelos dados, remover as colunas antigas — de modo que nenhum commit intermediário deixe o build quebrado.

**Tech Stack:** Next.js (App Router, Server Actions), Prisma + PostgreSQL 18 nativo, React Hook Form + Zod, Tailwind + shadcn/ui (Radix), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-08-20-tecnicos-design.md`

## Global Constraints

- **Técnico ≠ Vendedor ≠ Usuário.** Não reutilizar `Vendedor`. Não criar `usuarioId`, login, permissão ou agenda.
- **Campos do Técnico na V1: apenas `nome` e `ativo`** (mais `id`, `createdAt`, `updatedAt`). Nada de telefone, e-mail, cargo, comissão, custo/hora.
- **Não iniciar Pedido de Venda nem Ordem de Serviço.**
- **`onDelete: Restrict`** nas duas FKs. Nenhum `Cascade` parte de `Tecnico`.
- **Nunca editar migration antiga.** Só criar novas.
- **Backfill dirigido pelos dados.** Proibido hardcode de `"Vinicius"`. Proibido casar nomes por acento. Nome ambíguo ⇒ abortar a migration.
- **O snapshot nunca vem do navegador.** `responsavelNome` é lido do `Tecnico` persistido, dentro da transação — mesma regra do endereço (ADR-0400).
- **Regra do snapshot:** gravado na criação; **preservado** na edição que não troca o técnico; reescrito **somente** quando o `tecnicoId` muda.
- **Busca sem acento** usa a fonte única `@/utils/busca` (`normalizarBusca`/`contemBusca`). Proibido reescrever `.normalize()` em componente, hook ou service (ADR-0402).
- **Não corrigir** o comportamento equivalente de Vendedor inativo no workspace da Proposta. Registrar no BACKLOG.
- **`VERSION` não é alterada até a Task 11.**
- **Idioma:** identificadores, comentários, mensagens e docs em português, como todo o repositório.
- Ordem final do menu: `Dashboard · Clientes · Produtos · Propostas · Instalações · Vendedores · Técnicos · Configurações`.
- **Seletor de confirmação nas listagens CRUD:** o `CrudListView` passa
  `confirmLabel={type === "delete" ? "Excluir" : "Inativar"}` ao `ConfirmDialog`.
  Nos E2E de `/tecnicos`, confirmar é
  `page.getByRole("dialog").getByRole("button", { name: "Inativar" | "Excluir" })`
  — **nunca** `"Confirmar"`, que é o default usado apenas pela Cronologia.

## Nota de sequenciamento — por que três migrations e não uma

A spec (§4.2) descreve sete passos em ordem: criar tabela → colunas nullable → backfill → guarda → travar → FKs → remover colunas antigas. **A ordem é preservada integralmente.** O que muda é o empacotamento: os sete passos são distribuídos em três arquivos de migration para que nenhum commit intermediário deixe `npm run typecheck` quebrado.

| Migration | Passos da spec | Estado do repositório depois |
|---|---|---|
| A — `tecnicos` (Task 1) | 1 | Verde. Puramente aditivo. |
| B — `tecnicos_vinculo` (Task 5) | 2 a 6, mais `responsavel` deixa de ser `NOT NULL` | `lint` e testes verdes; **`typecheck`/`build` vermelhos por construção** até a Task 7 — ver a nota abaixo. |
| C — `tecnicos_drop_texto` (Task 9) | 7 | Verde. Só roda depois que nenhuma linha de código lê as colunas antigas. |

Sem esse split, a Task 5 derrubaria o build e ele só voltaria na Task 8 — quatro tarefas sem gate possível.

**Correção apurada durante a execução (2026-08-20).** O split reduz a janela, mas
não a elimina: tornar `tecnicoId`/`responsavelNome` obrigatórios no schema Prisma
faz o cliente gerado exigi-los em todo `create`, e o registro service só passa a
fornecê-los na Task 7. Logo `typecheck` e `build` ficam vermelhos **por
construção** durante as Tasks 5 e 6, e voltam ao verde na Task 7.

A alternativa — manter os campos opcionais no schema enquanto o banco já aplicou
`NOT NULL` — produz *drift*, e o próximo `migrate dev` tentaria desfazer o
`NOT NULL` ou ofereceria `reset` sobre dados reais. A janela é o mal menor, e é
explícita: cada tarefa afetada diz quais erros são esperados e em quais arquivos.
Erro fora dessa lista é regressão e interrompe a tarefa.

Puramente aditivo. Nenhuma tabela existente é tocada.

**Files:**

- Create: `prisma/migrations/20260820000000_tecnicos/migration.sql`

**Interfaces:**
- Consumes: nada.

- [ ] **Step 1: Acrescentar o model ao schema**

Em `prisma/schema.prisma`, logo **depois** do `model Vendedor` (fim da seção "Cadastros base"):

```prisma
/// Técnico — pessoa que executa ou acompanha o trabalho na Instalação.
///
/// NÃO é Vendedor (ADR-0408): um instalador não vende, e reaproveitar aquele
/// cadastro poluiria o autocomplete da Proposta e distorceria a regra de
/// exclusão "já foi usado em uma proposta".
///
/// NÃO é Usuário: não há login, permissão nem agenda. Quando houver
/// autenticação, "registrado por" será campo NOVO e aditivo, separado deste
/// vínculo — o Técnico responde por QUEM FEZ o trabalho, não por quem digitou.
model Tecnico {
  id    String  @id @default(cuid())
  ativo Boolean @default(true)
  nome  String

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  instalacoes Instalacao[]
  registros   InstalacaoRegistro[]

  @@index([ativo])
  @@map("tecnicos")
}
```

- [ ] **Step 2: Declarar o lado inverso das relações**

Sem isso o Prisma não valida o schema. Em `model Instalacao`, logo abaixo do bloco `proposta`:

```prisma
  /// Responsável ATUAL — estado corrente, não fato histórico. Renomear o
  /// Técnico DEVE refletir aqui; por isso não há snapshot textual (ADR-0408).
  tecnicoResponsavelId String?
  tecnicoResponsavel   Tecnico? @relation(fields: [tecnicoResponsavelId], references: [id], onDelete: Restrict)
```

e o índice, junto dos outros `@@index` do model:

```prisma
  @@index([tecnicoResponsavelId])
```

Em `model InstalacaoRegistro`, logo abaixo do campo `aconteceuEm`:

```prisma
  /// Quem executou/acompanhou. RESTRICT: técnico usado nunca é apagado.
  tecnicoId String?
  tecnico   Tecnico? @relation(fields: [tecnicoId], references: [id], onDelete: Restrict)

  /// Snapshot do nome do Técnico no momento em que ELE foi atribuído a este
  /// registro. Derivado NO SERVICE a partir do Tecnico persistido — nunca
  /// recebido do navegador. Vira obrigatório na Migration B.
  responsavelNome String?
```

e o índice:

```prisma
  @@index([tecnicoId])
```

> `tecnicoId` e `responsavelNome` nascem **opcionais** de propósito: a tabela tem linhas, e uma coluna `NOT NULL` sem default não pode ser adicionada a elas. A Migration B faz o backfill e só então aplica o `NOT NULL`. A Task 5 atualiza estas anotações.

```ts
import { prisma } from "@/infrastructure/database";
import { CANNOT_DELETE_USED_IN_INSTALACOES } from "@/lib/messages";

/**
 * Serviço de Técnicos (Sprint 4.1, ADR-0408).
 *
 * Molde de `vendedor.service.ts`, com dois campos a menos. A diferença real
 * está na regra de exclusão: Técnico é usado em DOIS lugares — como responsável
 * atual da Instalação e como responsável de cada registro da cronologia —, e
 * ambos contam.
 *
 * Técnico NÃO é Vendedor e NÃO é Usuário. Não há login, permissão nem agenda.
 */

export interface TecnicoListItem {
  id: string;
  ativo: boolean;
  nome: string;
}

export interface TecnicoFormDTO {
  ativo: boolean;
  nome: string;
}

export interface TecnicoInput {
  ativo: boolean;
  nome: string;
}

/** Opção de `Select` — mesmo formato do `SelectOption` de `proposta.service`. */
export interface TecnicoOption {
  value: string;
  label: string;
}

export { CANNOT_DELETE_USED_IN_INSTALACOES };

export async function listTecnicos(
  showInactive: boolean,
): Promise<TecnicoListItem[]> {
  return prisma.tecnico.findMany({
    where: showInactive ? {} : { ativo: true },
    select: { id: true, ativo: true, nome: true },
    orderBy: { nome: "asc" },
  });
}

export async function getTecnicoForEdit(
  id: string,
): Promise<TecnicoFormDTO | null> {
  const t = await prisma.tecnico.findUnique({
    where: { id },
    select: { ativo: true, nome: true },
  });
  return t ?? null;
}

export async function createTecnico(input: TecnicoInput): Promise<string> {
  const created = await prisma.tecnico.create({
    data: { ativo: input.ativo, nome: input.nome.trim() },
    select: { id: true },
  });
  return created.id;
}

export async function updateTecnico(
  id: string,
  input: TecnicoInput,
): Promise<void> {
  await prisma.tecnico.update({
    where: { id },
    data: { ativo: input.ativo, nome: input.nome.trim() },
  });
}

/**
 * Exclusão permitida apenas para técnico NUNCA usado — o padrão de Cliente,
 * Produto e Vendedor. "Usado" é referenciado pela Instalação OU por qualquer
 * registro da cronologia.
 *
 * A checagem existe aqui mesmo com o `onDelete: Restrict` no banco: o Restrict
 * protege qualquer caminho de escrita, mas devolve erro de FK. É esta função que
 * produz a mensagem que orienta o usuário a inativar.
 */
export async function removeTecnico(id: string): Promise<void> {
  const [emInstalacoes, emRegistros] = await Promise.all([
    prisma.instalacao.count({ where: { tecnicoResponsavelId: id } }),
    prisma.instalacaoRegistro.count({ where: { tecnicoId: id } }),
  ]);
  if (emInstalacoes + emRegistros > 0) {
    throw new Error(CANNOT_DELETE_USED_IN_INSTALACOES);
  }
  await prisma.tecnico.delete({ where: { id } });
}

export async function setTecnicoAtivo(
  id: string,
  ativo: boolean,
): Promise<void> {
  await prisma.tecnico.update({ where: { id }, data: { ativo } });
}

/**
 * Opções para o `Select` de responsável: **ativos ∪ os ids informados**.
 *
 * `incluirIds` carrega os técnicos já vinculados àquele agregado, mesmo
 * inativos. Sem eles, abrir uma Instalação cujo técnico foi inativado mostraria
 * o campo em branco, e salvar qualquer outra alteração apagaria o vínculo em
 * silêncio. Inativo aparece rotulado, para não ser escolhido por engano em um
 * vínculo novo.
 */
export async function listTecnicoOptions(
  incluirIds: string[] = [],
): Promise<TecnicoOption[]> {
  const ids = [...new Set(incluirIds.filter(Boolean))];
  const rows = await prisma.tecnico.findMany({
    where: { OR: [{ ativo: true }, { id: { in: ids } }] },
    select: { id: true, nome: true, ativo: true },
    orderBy: { nome: "asc" },
  });
  return rows.map((t) => ({
    value: t.id,
    label: t.ativo ? t.nome : `${t.nome} (inativo)`,
  }));
}
```

export async function createTecnicoAction(
  values: unknown,
): Promise<ActionResult<{ id: string }>> {
  const parsed = tecnicoSchema.safeParse(values);
  if (!parsed.success) {
    return fail("Dados inválidos. Verifique os campos destacados.");
  }
  try {
    const id = await createTecnico(parsed.data);
    revalidatePath("/tecnicos");
    return ok({ id });
  } catch (error) {
    return fail(error instanceof Error ? error.message : "Falha ao salvar.");
  }
}

export async function updateTecnicoAction(
  id: string,
  values: unknown,
): Promise<ActionResult> {
  const parsed = tecnicoSchema.safeParse(values);
  if (!parsed.success) {
    return fail("Dados inválidos. Verifique os campos destacados.");
  }
  try {
    await updateTecnico(id, parsed.data);
    revalidatePath("/tecnicos");
    return ok(undefined);
  } catch (error) {
    return fail(error instanceof Error ? error.message : "Falha ao salvar.");
  }
}

export async function deleteTecnicoAction(id: string): Promise<ActionResult> {
  try {
    await removeTecnico(id);
    revalidatePath("/tecnicos");
    return ok(undefined);
  } catch (error) {
    // A mensagem do bloqueio chega ao usuário como está — é ela que orienta
    // a inativar em vez de excluir.
    return fail(error instanceof Error ? error.message : "Falha ao excluir.");
  }
}

export async function toggleTecnicoAtivoAction(
  id: string,
  ativo: boolean,
): Promise<ActionResult> {
  try {
    await setTecnicoAtivo(id, ativo);
    revalidatePath("/tecnicos");
    return ok(undefined);
  } catch (error) {
    return fail(error instanceof Error ? error.message : "Falha ao atualizar.");
  }
}

export function TecnicoForm({ tecnicoId, defaultValues }: TecnicoFormProps) {
  const router = useRouter();
  const [saving, setSaving] = useState(false);
  const isEdit = Boolean(tecnicoId);

      title={isEdit ? "Editar técnico" : "Novo técnico"}
      description="Preencha os dados do técnico."

      onSubmit={onSubmit}
      onCancel={() => router.push("/tecnicos")}

Escreva `prisma/migrations/20260820010000_tecnicos_vinculo/migration.sql`. É SQL manual de propósito: o diff automático do Prisma não sabe fazer backfill, e emitiria `SET NOT NULL` antes de haver dado.

```sql
-- Sprint 4.1 — vínculo do responsável com o cadastro de Técnicos (ADR-0408).
--
-- Supersede parcial do ADR-0400, que definia o responsável como TEXTO LIVRE.
-- O princípio daquele ADR — não reescrever silenciosamente o histórico
-- operacional — é preservado por `responsavelNome`, o snapshot que acompanha
-- o vínculo estrutural.
--
-- CONTEÚDO AUDITADO ANTES DO BACKFILL (2026-08-20), linha a linha:
--   instalacoes           1 linha  → nº 1045, "responsavelAtual" = NULL
--   instalacao_registros  3 linhas → todas "Vinicius" (instalação 1045)
--   nomes distintos (minúsculas, espaços colapsados): 1
--     vinicius -> ["Vinicius"] (3 usos)
--   Nenhuma variação de caixa/espaço. Nenhum valor ambíguo ou duvidoso.
--
-- Ainda assim o backfill abaixo é DIRIGIDO PELOS DADOS, não escrito para este
-- conteúdo: a mesma migration precisa estar correta em qualquer banco
-- restaurado de backup. Nenhum nome está hardcoded.
--
-- Esta migration NÃO remove coluna nenhuma. Os dois DROP ficam na migration
-- seguinte (`tecnicos_drop_texto`), que só roda depois que nenhuma linha de
-- código lê os campos antigos.

-- ---------------------------------------------------------------------------
-- 1. Um Técnico por nome DISTINTO encontrado nos dois campos de texto.
--
-- Chave de agrupamento: minúsculas + sem espaço nas pontas + espaços internos
-- colapsados. Agrupa "carlos", "Carlos" e "Carlos  " no mesmo Técnico.
--
-- A chave NÃO remove acento, DE PROPÓSITO: "Joao" e "João" podem ser a mesma
-- pessoa ou não, e inventar essa correspondência é justamente o que a decisão
-- proíbe. Viram Técnicos distintos, visíveis no cadastro, onde uma PESSOA
-- decide se os funde — isso é decisão de negócio, não de migration.
--
-- `gen_random_uuid()` é nativo do PostgreSQL desde a 13 (aqui roda 18): não
-- exige extensão nem superusuário, o que respeita o ADR-0101. `cuid()` não
-- serviria: é gerado pelo Prisma no cliente, não existe como default no banco.
-- O id nunca é exibido.
-- ---------------------------------------------------------------------------
INSERT INTO "tecnicos" ("id", "nome", "ativo", "createdAt", "updatedAt")
SELECT DISTINCT ON (lower(regexp_replace(btrim(nome), '\s+', ' ', 'g')))
       gen_random_uuid()::text,
       btrim(nome),
       true,
       now(),
       now()
  FROM (
         SELECT "responsavel" AS nome
           FROM "instalacao_registros"
          WHERE "responsavel" IS NOT NULL
         UNION ALL
         SELECT "responsavelAtual" AS nome
           FROM "instalacoes"
          WHERE "responsavelAtual" IS NOT NULL
       ) AS origem
 WHERE btrim(nome) <> ''
 ORDER BY lower(regexp_replace(btrim(nome), '\s+', ' ', 'g')), btrim(nome);

-- ---------------------------------------------------------------------------
-- 2. Vincula os registros da cronologia.
--
-- `responsavelNome` recebe o TEXTO ORIGINAL DAQUELA LINHA, não o nome canônico
-- do Técnico: se três registros diziam "Carlos", "carlos" e "Carlos ", os três
-- apontam para o mesmo Técnico e CADA UM mantém a própria grafia. É a leitura
-- mais fiel possível do histórico.
-- ---------------------------------------------------------------------------
UPDATE "instalacao_registros" r
   SET "tecnicoId" = t."id",
       "responsavelNome" = r."responsavel"
  FROM "tecnicos" t
 WHERE lower(regexp_replace(btrim(t."nome"), '\s+', ' ', 'g'))
     = lower(regexp_replace(btrim(r."responsavel"), '\s+', ' ', 'g'));

-- ---------------------------------------------------------------------------
-- 3. Vincula as instalações. SEM snapshot: "responsável atual" é estado
--    corrente, e renomear o Técnico deve refletir ali (ADR-0408).
-- ---------------------------------------------------------------------------
UPDATE "instalacoes" i
   SET "tecnicoResponsavelId" = t."id"
  FROM "tecnicos" t
 WHERE i."responsavelAtual" IS NOT NULL
   AND lower(regexp_replace(btrim(t."nome"), '\s+', ' ', 'g'))
     = lower(regexp_replace(btrim(i."responsavelAtual"), '\s+', ' ', 'g'));

-- ---------------------------------------------------------------------------
-- 4. GUARDA. Abortar é o comportamento correto: em um banco com nome que a
--    chave não resolve, é preferível a migration falhar e alguém olhar, a ela
--    inventar um mapeamento. O Prisma roda cada migration em transação, então
--    a exceção reverte TUDO — inclusive os INSERT/UPDATE acima.
-- ---------------------------------------------------------------------------
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM "instalacao_registros" WHERE "tecnicoId" IS NULL) THEN
    RAISE EXCEPTION
      '[tecnicos] backfill incompleto em instalacao_registros — migration abortada, nada foi alterado';
  END IF;

  IF EXISTS (SELECT 1
               FROM "instalacoes"
              WHERE "responsavelAtual" IS NOT NULL
                AND "tecnicoResponsavelId" IS NULL) THEN
    RAISE EXCEPTION
      '[tecnicos] backfill incompleto em instalacoes — migration abortada, nada foi alterado';
  END IF;
END $$;

-- ---------------------------------------------------------------------------
-- 5. Só agora: travar as colunas novas.
-- ---------------------------------------------------------------------------
ALTER TABLE "instalacao_registros" ALTER COLUMN "tecnicoId"       SET NOT NULL;
ALTER TABLE "instalacao_registros" ALTER COLUMN "responsavelNome" SET NOT NULL;

-- ---------------------------------------------------------------------------
-- 6. A coluna ANTIGA continua existindo, mas deixa de ser obrigatória, para que
--    o código possa parar de escrevê-la antes do DROP da próxima migration.
-- ---------------------------------------------------------------------------
ALTER TABLE "instalacao_registros" ALTER COLUMN "responsavel" DROP NOT NULL;
```

> As FKs, os índices e a `CREATE TABLE` já vieram na Migration A. Se por algum motivo o Prisma não as tiver emitido lá, acrescente-as aqui, antes do passo 5.

/**

export async function listTecnicoOptionsDaInstalacao(
  instalacaoId: string,
): Promise<TecnicoOption[]> {
  const i = await prisma.instalacao.findUnique({

      registros: { select: { tecnicoId: true } },

    ...(i.tecnicoResponsavelId ? [i.tecnicoResponsavelId] : []),
    ...i.registros.map((r) => r.tecnicoId),
  ]);
}

- [ ] **Step 7: Criar o campo compartilhado de seleção de Técnico**

`SelectField` liga direto ao RHF, não trata `null` e não oferece sentinela de

```tsx
"use client";

import { useFormContext } from "react-hook-form";

import {
  FormControl,
  FormField,
  FormItem,
  FormLabel,
  FormMessage,
} from "@/components/ui/form";
import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from "@/components/ui/select";
import type { TecnicoOption } from "@/services/tecnico.service";

/** Sentinela de "sem técnico" — o Select do shadcn não aceita value vazio. */
const NENHUM = "__none__";

/**
 * Escolha do Técnico responsável (ADR-0408) — mesmo padrão do Vendedor no
 * cabeçalho da Proposta: `Select` alimentado no servidor com os ativos.
 *
 * As opções chegam prontas do service e já incluem os técnicos INATIVOS que
 * estejam vinculados, rotulados "(inativo)". É isso que impede o campo de
 * aparecer em branco quando alguém inativa um técnico já usado.
 */
export function TecnicoSelectField({
  name,
  label,
  options,
  opcional = false,
  disabled = false,
}: {
  name: string;
  label: string;
  options: TecnicoOption[];
  /** Quando true, oferece "Nenhum" e o valor pode ser null. */
  opcional?: boolean;
  disabled?: boolean;
}) {
  const { control } = useFormContext();

  return (
    <FormField
      control={control}
      name={name}
      render={({ field }) => (
        <FormItem>
          <FormLabel>{label}</FormLabel>
          <Select
            value={field.value ?? (opcional ? NENHUM : "")}
            onValueChange={(v) => field.onChange(v === NENHUM ? null : v)}
            disabled={disabled}
          >
            <FormControl>
              <SelectTrigger>
                <SelectValue placeholder="Selecione o técnico" />
              </SelectTrigger>
            </FormControl>
            <SelectContent>
              {opcional && <SelectItem value={NENHUM}>Nenhum</SelectItem>}
              {options.map((o) => (
                <SelectItem key={o.value} value={o.value}>
                  {o.label}
                </SelectItem>
              ))}
            </SelectContent>
          </Select>
          <FormMessage />
        </FormItem>
      )}
    />
  );
}
```
